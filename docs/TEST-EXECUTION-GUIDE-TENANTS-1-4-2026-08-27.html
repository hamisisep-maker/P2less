Before you start

Ground rules

Read once, applies to every tenant below.

What you'll need
  • A browser (any modern one), pointed at https://p2less-app-production.up.railway.app.
  • Four throwaway test identities — a name, an @example.com-style email, and an obviously-fake phone number for each tenant. Suggested pattern: +254700111001 for Tenant 1, ...002 for Tenant 2, and so on.
  • An admin login for whoever plays the "Tech" role in the steps marked that way.
  • Nothing else. No AI provider usage happens anywhere in this guide — every reply path used below is deterministic (menu numbers, OTP codes, templated lookups), never a real AI call.
Why the OTP code shows on screen Production doesn't have a real SMS provider configured yet, so the sign-up flow honestly labels this "Demo only" and prints the real 6-digit code directly on the page instead of texting it. This is the actual, current, honest behavior of the app — not a workaround for this test.

Tool primer, part 1

Chrome DevTools, from zero

You won't need this for most of the guide — the on-screen messages are usually enough. It's here for the moments where you want to see the real, underlying server response with your own eyes.

  1. You — DevTools
    With Chrome open on any page, press F12. (If nothing happens, right-click the page → Inspect.)Expect: a panel opens with tabs across the top — Elements, Console, Network, Application, and more.
  2. You — DevTools
    Click Network, then tick Preserve log so the list doesn't clear as you navigate.
  3. You — DevTools
    Click any row in the list to see its Status code and its Response tab — the server's actual reply. A 200 means it succeeded; a 400/401/403 means it was refused; a 500 means the server itself broke. The Response tab often has a short, readable message explaining exactly which of those happened and why.
Tool primer, part 2

The admin console, from zero

Whoever plays the Tech role for admin-side checks should be comfortable here before Tenant 1 even signs up.

  1. Tech
    Log into P2Less as a platform admin, then go to /admin/tenants.Expect: a list of every tenant on the platform, each row showing its name, plan, and status at a glance.
  2. Tech
    Click any tenant's row.Expect: that tenant's own detail page — plan, subscription status, owner contact, and (depending on what's built) recent activity.
  3. Tech
    Go to /admin/billing.Expect: a platform-wide list of invoices and payments, each tied back to a tenant, with amounts and statuses.
  4. Tech
    Note the URL pattern for each — you'll be asked to revisit these exact pages, filtered to a specific tenant, throughout this guide.
Tool primer, part 3

Prisma Studio, from zero

The one tool this guide asks an engineer to actually install and run. It's already part of the project — nothing new to download.

  1. Tech
    Open a terminal in the project's folder (p2less-platform) and run npx prisma studio.Expect: a message that it's running, and a browser tab opens automatically at localhost:5555.
  2. Tech
    On the left, you'll see every table in the database — Tenant, Subscription, Payment, Invoice, UsageEvent, AiRequestLog, and more. Click any one to see its rows as an editable spreadsheet.
  3. Tech
    To add a row: click Add record (usually top-right), fill in the fields shown, click Save 1 change. To edit one: click directly into any cell, change it, save the same way.
  4. Tech
    Leave this tab open for the whole guide — you'll come back to it for every step tagged "Tech."
Be careful with this toolIt has full read/write access to the real production-shaped database you point it at. Every "Tech" step in this guide tells you exactly which table and which fields to touch — stick to those, and double-check you're pointed at the intended database (test/staging, not a real customer's data) before saving anything.
Tenant 1

WhatsApp Only → Starter

A small business signing up, connecting WhatsApp, and upgrading to the cheapest paid tier.

Sign up

  1. You — Browser
    Open a browser and go to p2less-app-production.up.railway.app/onboard.Expect: a page titled "Your conversational platform, ready in minutes," with a 3-step outline (Tell us about your organization · Verify your phone · Start exploring).
  2. You — Browser
    Scroll to the form. In Organization name, type Tenant 1 — WhatsApp Only. Leave Industry as Business.
  3. You — Browser
    In Your phone number, type your Tenant 1 test number, e.g. +254700111001.
  4. You — Browser
    Fill Your name and Your email with your Tenant 1 test identity, then click Create my workspace.Expect: the page advances to "Verify your phone number," with an orange "Demo only" box showing a real 6-digit code.
  5. You — Browser
    Type that exact code into the 6-digit code field and click Verify and create workspace. Wait for the page to finish — don't navigate away.How to know it worked: you land signed-in, on either /explore or the real dashboard, with a visible "Welcome" heading. If instead you're bounced back to the OTP screen, the code was mistyped or already used — reload /onboard and start over from a clean state rather than retrying the same code.

Check the trial is real

  1. You — Browser
    Go to /dashboard. Look at the card titled Free trial balance near the top.Expect: a badge reading "7 days left" (or close to it), and two progress bars both showing 0 / 200 and 0 / 100.
  2. Tech — Prisma Studio
    In the already-open Prisma Studio tab, click the Subscription table, find Tenant 1's row (match it by its tenantId, cross-referenced from the Tenant table by name), and look at its trialEndsAt column.How to know it's right: a real date roughly 7 days from today, not blank/null.

Connect WhatsApp

  1. You — Browser
    In the left sidebar, click Channels.
  2. You — Browser
    Under the WhatsApp section, click Connect via alternative (the camera-free, typed-pairing-code path is the most reliable one to test with).
  3. You — Browser
    Optionally type a real WhatsApp number of your own into "Camera not working? Enter your WhatsApp number," then submit.How to know it worked: a "Scan to connect" modal opens showing either a QR code or a typed pairing code, and stays open (this exact modal not disappearing on its own was a real bug found and fixed earlier this week — worth specifically confirming it still holds by waiting 15–20 seconds without clicking anything and checking it hasn't vanished).
  4. You — Browser
    If you have a real phone free to pair, finish linking it. If not, close the modal and note that connection was left pending — that's a legitimate, logged outcome, not a failure of this step.

Upgrade to Starter

  1. You — Browser
    Go to /dashboard/billing. Find the Starter row and click Upgrade.Expect: a modal opens, briefly says "Calculating your upgrade…," then shows a real invoice: Invoice number, Current plan (Trial allowance), Current plan value KES 0, Starter plan price KES 1,500, Amount payable KES 1,500.
  2. You — Browser
    Click M-Pesa STK Push, enter a real or test phone number, click Pay KES 1,500.Expect (demo mode): "Recorded (demo mode)… Your upgrade is now active" almost immediately, since no real Daraja keys are configured. Expect (if Daraja IS configured): a real STK prompt on the phone — approve it, then wait for the page to detect confirmation.
  3. You — Browser
    Once the modal shows "Payment confirmed," click Done, then reload /dashboard.How to know it worked: the subtitle under "Welcome" now reads "… · Starter plan," and the usage card now shows a real KES balance instead of the trial progress bars. If the subtitle still says trial after a reload, the payment didn't actually settle — check DevTools' Network tab response for the payment request for a clearer reason.
Verify before moving on
  • Tech — Admin console: go to /admin/tenants, find Tenant 1's row.Expect: plan column reads "Starter," status "active," owner email matches what you signed up with.
  • Tech — Admin console: go to /admin/billing, filter or search for Tenant 1.Expect: one real payment of KES 1,500 against this tenant, status "paid" or equivalent.
  • You — Browser: reload the Channels page.Expect: WhatsApp's real connection status shown accurately — connected, pending, or not connected, matching whatever you actually did above, never a stale or mismatched badge.

Tenant 3

Telegram Only → Business

The easiest channel to connect for real — genuinely free and instant, no excuse to skip it.

Sign up & verify trial

  1. You — Browser
    Repeat sign-up as Tenant 3 — Telegram Only, phone e.g. +254700111003. Confirm the trial card.

Connect Telegram

  1. You — Telegram app
    On your own phone or Telegram Desktop, message @BotFather, send /newbot, follow its prompts, and copy the token it gives you.How to know it worked: BotFather's final message includes a long token string starting with a number, a colon, then letters and digits.
  2. You — Browser
    In P2Less, go to Channels → Telegram, paste the token into Connect bot, submit.Expect: the section shows a real connected bot username, no approval wait of any kind.
  3. You — Telegram app
    From your own Telegram, message the bot something a deterministic path can answer (e.g. a number from its menu) — not a free-form question that would need a real AI call.How to know it worked: the bot replies within a few seconds with the expected menu response.

Upgrade to Business

  1. You — Browser
    Same upgrade flow, Business row, confirm invoice KES 19,900, complete payment.
Verify before moving on
  • You — Browser: go to /dashboard/conversations.Expect: the real inbound Telegram message you sent actually appears as a Conversation with at least one Message.

Payment edge cases

What happens when money gets messy

These situations are real, but none of them can be produced by simply clicking through the UI in real time — they're staged directly in Prisma Studio, then observed through the same UI a real customer would see.

A partial payment lands

  1. You — Browser
    Pick one tenant with an open invoice (e.g. start a fresh upgrade on Tenant 2 without paying yet). Note the invoice's payableKes value shown on screen.
  2. Tech — Prisma Studio
    Click the Payment table, click Add record. Set invoiceId to that invoice's id (copy it from the Invoice table, matching by tenant and creation time), set amountKes to something less than the full amount owed — e.g. half of it — set status to whatever value the table uses for "confirmed" (check an existing paid row for the exact spelling), save.
  3. You — Browser
    Reopen that tenant's upgrade modal.How to know it worked: it shows "We received KES X toward this invoice — KES Y still due," and does not claim the plan has changed. If it instead shows the plan as upgraded already, that's a real bug — a partial payment must never be treated as a full one.

Paid, but the money hasn't arrived yet

  1. You — Browser
    Start a real STK payment and, instead of approving it, just wait past the confirmation window without doing anything on the phone.Expect: after ~90 seconds, the modal honestly says it's still waiting and offers to try again — never a false "success."
  2. Tech — Prisma Studio
    Minutes later, add the real Payment row as if it had arrived late (same steps as the partial-payment case above, but for the full amount this time), then, from a terminal in the project folder, run the real settlement function directly — ask your engineer for the exact one-off script command, since it calls internal code rather than clicking a button.How to know it worked: reload the tenant's dashboard — it should now show the upgraded plan, even though the original request had already timed out on screen. A late arrival must still count.

Payment fails or is cancelled

  1. You — Browser
    Start a real STK payment and cancel/decline it on the phone (or simulate a decline).How to know it worked: "Payment was cancelled or failed. Your plan has not changed" — and reloading the dashboard confirms the plan genuinely didn't move.
Three simulated months

A realistic usage history, without any real AI cost

Entirely a Prisma Studio job — there's no honest way to "click" three months into existence. What matters is that what gets inserted is realistic and checkable.

  1. Tech — Prisma Studio
    For each of Tenants 1–4, click the UsageEvent table, Add record repeatedly (or, if your Prisma Studio version supports pasting multiple rows, use that) to insert rows dated across a 3-month span, at a volume appropriate to their plan — deliberately including one month where one tenant's volume crosses their real cap. Set each row's tenantId and createdAt deliberately, in the past.
  2. Tech — Prisma Studio
    Click the AiRequestLog table, insert a handful of rows with realistic totalTokens/costUsd figures matching the real ModelPricing table (check its values first) — never by calling a real AI provider.
  3. You — Browser
    For each tenant, send a small number of genuinely real messages over a deterministic path (a menu tap, an OTP entry, a templated lookup) — enough to confirm the real send pipeline works, not enough to represent the full 3 months.
The real questions this answers
  • You — Browser: for the tenant whose volume crossed their cap, does the dashboard actually show them blocked that month, and correctly reset the next?
  • You — Browser: do the dashboard's message-volume chart and usage numbers match what was actually inserted in Prisma Studio?
  • Tech — Admin console: does /admin's platform-wide view aggregate all four tenants correctly — do the totals shown there actually add up to what you inserted per tenant?
  • Tech — Prisma Studio + Admin console: compare the costUsd sums in AiRequestLog against the real KES revenue shown in /admin/billing for the same tenants and period — is revenue genuinely higher than cost, per tenant, and as one platform total?
  • Tech — Admin console: does the audit trail account for every plan change, payment, and balance movement across the whole period, with the tamper-evident hash chain still holding?
