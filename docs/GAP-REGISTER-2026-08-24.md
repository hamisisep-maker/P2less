# P2Less — Gap Register (the one current, evidence-backed list)

**Why this exists**: the user raised a serious, legitimate concern 2026-08-24 — a real production bug (two tenants able to both claim the same Facebook Page, with nothing in the database preventing it) surfaced a broader worry about missing CRUD operations, unenforced money/billing logic, and whether prior audit work was actually being tracked anywhere real. Investigation confirmed: a formal "Master Gap Register" audit *was* done 2026-08-23, but its findings were scattered across ~70 sections of `docs/OPERATIONS-GUIDE-2026-08-23.md` with no single current-status document — and several items marked "deferred" in an early section were quietly fixed in a *later* section of the same file, with no cross-reference. This document is the fix for that: one place, every known gap, current status verified against real code today, not copied from an old note.

**How to keep this honest going forward**: when a gap gets fixed, update its entry here directly (status + what fixed it + evidence) rather than leaving a stale note and writing a fresh mention somewhere else. When a new gap is found, add it here in the right category. This document is what gets checked first, not re-derived from scratch, the next time this kind of audit is asked for.

**Every item below carries real evidence** — either a direct code citation from today's re-verification, or (for the historical batch) a citation confirmed by an agent that read all 70 operations-guide sections and independently re-checked each claim against the current source tree, not just copied the guide's old text.

## Found and fixed today (2026-08-24 / 2026-08-25)

### 1. Two tenants could both claim the same real external Page/bot/number — real production incident
- **Category**: security / data-integrity
- **What happened**: a real customer test revealed Hamzone Technologies' actual Facebook Page (`828105030394804`) was bound to the wrong tenant (Riverside Academy) — a message to the real Page got answered as if it were Riverside's school-onboarding bot, not Hamzone's.
- **Root cause, confirmed in the code, not assumed**: `Channel.@@unique([tenantId, type])` only ever stopped one tenant from having two Messenger channels. The `address` field itself (the real Page ID) had zero uniqueness constraint — only a non-unique lookup index. Nothing in the database prevented two different tenants from both owning the same real external identity, and the webhook resolves the owning tenant via `findFirst()` with no tiebreaker — meaning if it ever happened again, routing between the two tenants would be nondeterministic, not just wrong once.
- **Fixed**: removed the incorrect Channel row (Riverside's), then added `@@unique([type, address])` to the schema — the database itself now refuses a second tenant claiming an address another tenant already owns. Verified directly: a duplicate-create attempt now throws a real `P2002` constraint violation, not just a hoped-for check in application code.
- **A real deploy incident happened while shipping this** — see the entry below.

### 2. A real production deploy incident, caused by shipping the fix above
- **Category**: other (process/infrastructure)
- **What happened**: `prod-start.mjs`'s boot-time `prisma db push` crash-looped production for approximately one minute. Prisma's static safety check flags *any* new unique constraint as a potential data-loss risk regardless of whether real duplicates exist — already independently verified zero duplicates existed before the schema change shipped, but the check doesn't know that in advance.
- **Caught via a direct health check**, not by trusting the deploy tool's own status label — Railway's `deployment list` showed "SUCCESS" while the container was actively crash-looping underneath it.
- **Fixed**: a one-time `--accept-data-loss` flag for exactly one boot, confirmed via the real boot log that the schema synced cleanly with no error, then reverted immediately so future genuinely-destructive changes are still caught. A permanent comment now lives in `scripts/prod-start.mjs` documenting exactly what happened and the safe procedure to follow if this specific class of false-positive refusal happens again.

### 3. RESOLVED, 2026-08-24 — subscription cancellation now exists, admin-only
- **Category**: money-billing
- **Finding**: `cancelled` existed as a `Subscription.status` value with its own badge color on the tenant billing page, but nothing anywhere ever set it — no tenant-facing button, no admin-facing one either.
- **Real design work done, not guessed at**: a self-service version was built first (tenant-initiated, cutoff gated behind a real-time M-Pesa settlement payment), then walked through what actually happens if that payment is never completed — a tenant who ignores the STK PIN prompt would stay fully active, still costing Hamzone real Meta/AI money, indefinitely, since the subscription would still read "active" to `runBillingCycle()` and the existing non-payment grace-period machinery wouldn't engage until the next natural renewal date (potentially weeks away). Corrected mid-build: cutoff must be unconditional and immediate, payment collection fully decoupled from it. Then redirected entirely: self-service cancellation was rejected outright in favor of admin-only, and the settlement mechanism itself was reconsidered — an automated real-time M-Pesa push at the exact moment a subscription is being cancelled isn't the right moment for that; instead the final cycle's usage is billed (a real `Payment` row, `status: "pending"`, `purpose: "cancellation"`), emailed to the tenant's owner as an itemized invoice via Resend, and recorded in the audit trail — collected afterward like any other outstanding invoice, not pushed for in the moment.
- **Shipped**: `cancelTenantSubscriptionAction` (`admin-actions.ts`), gated by a new `tenants.cancel` permission (held by `super_admin`/`operations_admin`, deliberately not `support_admin`), wired into `/admin/tenants` next to Suspend/Reactivate with the same required-reason confirm pattern. `finalizeCancellation()` (`billing-lifecycle.ts`) is the actual cutoff — sets `Tenant.status`/`Subscription.status` to `"cancelled"`, reusing the same access-gate `conversation.ts` already used for `"suspended"` (now recognizing both). Guarded against a real race found while designing this: a renewal charge already in flight when a tenant is cancelled can still resolve afterward via the M-Pesa webhook — `handleSubscriptionPaymentConfirmed`/`recordFailedPayment` now both check for an already-cancelled subscription first and skip reactivation/retry-scheduling, so a stray late payment can never silently undo a real cancellation.
- **Verified live**, not just typechecked: cancelled a real seeded tenant (Nairobi Hospital) end to end as the real super admin — `Tenant.status`/`Subscription.status` both flipped to `cancelled`, the webchat access gate immediately returned "This number is not in service," the `Payment` row and privileged-action audit entry both recorded the correct outstanding amount (KES 20,519, real usage-based), and the email attempt hit Resend's real API and failed *honestly* with a real, informative error (sandbox mode only sends to the account's own verified address) — recorded in the audit detail, not silently swallowed. Production needs a verified Resend sending domain before this email is actually deliverable to real tenant addresses — a real, separate follow-up, not a code bug.
- **Deliberately not built this round**: a way for a tenant to pay off an old cancellation invoice online — an admin with `billing.confirm_payment` resolves it manually once money arrives by whatever channel, same as any other manual reconciliation today.

### 4. RESOLVED, 2026-08-25 — plan changes now exist, split by direction and risk
- **Category**: money-billing
- **Finding**: `updatePlanAction` (`src/lib/admin-actions.ts`) looked like the answer at first read, but it edits the **global plan definition** (Professional's price, its limits) — not which plan a specific tenant is assigned to. Grepped every `Subscription` update across the codebase specifically for `planId`: it's set once at signup (`finalizeOnboarding`) and never touched again by any code path, anywhere.
- **Real trap found before building anything**: `computeBill()` reads `plan.priceMonthly` fresh against usage counted since the start of the *calendar* month, with no record of which plan was active on which days. An immediate plan change mid-cycle would silently apply the new rate to the whole month, including days spent on the old plan — no proration mechanism exists anywhere in this codebase (confirmed when cancellation was built), so this isn't something to quietly patch, it's a real decision.
- **Also found while designing it**: `Plan.priceMonthly` alone can't determine upgrade vs. downgrade — checked the real seed data first: Enterprise prices at 0 (same as Free) but is obviously the top tier. `Plan.sort`, the field that exists specifically for tier ordering, is what direction is read from instead.
- **Design landed on, split by real risk**: upgrades are tenant self-service (`upgradeSubscriptionPlanAction`, `actions.ts`) and apply **immediately** — an explicit, honest "the whole current bill charges the new rate, no partial-month credit" rule, safe because it only ever increases revenue. Downgrades are **admin-only** (`changeTenantPlanAction`, gated by a new `tenants.change_plan` permission) and are **deferred to the next renewal** (`Subscription.pendingPlanId`, applied by `runBillingCycle()` right as the old cycle ends) — closes the exact gaming risk of downgrading right before a bill is computed to shrink what's owed for usage already incurred at the higher rate.
- **Verified live**, not just typechecked: upgraded a real seeded Free-tier tenant (Kilimani Retail) self-service — plan fee and total bill updated immediately and correctly (KES 619 → KES 5,519, exactly the Professional plan fee difference). Scheduled an admin-initiated downgrade on the same tenant — confirmed `planId` stayed on the old plan and `pendingPlanId` was set (not applied immediately). Forced `renewsAt` into the past and ran the real billing cycle (via the same `runCrossTenant` wrapping `runJobNow()` uses, not a shortcut) — confirmed the downgrade applied at exactly that point, `pendingPlanId` cleared, both the scheduling and application steps recorded as distinct audit entries.
- **Deliberately not built this round**: true proration (a blended mid-cycle rate) — consistent with cancellation's same choice, no proration infrastructure exists anywhere in this billing model yet.

### 5. IN PROGRESS, 2026-08-25 — prepaid billing redesign (post-paid → real KES balances)
- **Category**: money-billing
- **Why**: direct founder request — the old post-paid model (`computeBill()`/`runBillingCycle()`) let usage accumulate all month with payment only collected at renewal, leaving Hamzone exposed to a real, unbounded cost if a tenant never pays. Redesigned so every real, non-Enterprise plan draws down two separate prepaid KES balances (`Subscription.messageBalanceKes`/`aiBalanceKes`) checked **before** the real external cost (the actual WhatsApp send, the actual AI provider call), never after. Enterprise (`Plan.postpaidUsage`) keeps the original post-paid model untouched — a negotiated-contract trust tier. Trial is a state (`Subscription.status === "trial"`), not a plan — no `Plan` row is ever presented to a customer as "Free"; the existing "free" `Plan` row is repurposed as an internal-only, admin-configurable trial allowance reusing the existing `checkLimit()` count mechanism.
- **Shipped and live-verified**: schema (`messageBalanceKes`/`aiBalanceKes`/low-balance-notified timestamps/`balanceMigratedAt`), four real plans (Starter/Professional/Business/Enterprise) plus the internal trial allowance, channels free/unlimited on every tier (connectors keep their existing per-tier cap — deliberately NOT the same thing), the message-balance gate wired into `handleInbound` (`conversation.ts`), and — the real gap found and fixed today — the AI-balance gate/debit centralized inside `callLLM()` itself (`ai.ts`), the single real choke point every AI-calling function goes through (`understand`, commerce classification, order-step, FAQ extraction, `humanizeReply`, `smallTalk`, tool completions). First implementation only wired `understand()`'s call sites; live-verified with a real WhatsApp-style message that `smallTalk` produced an unmistakably AI-generated reply while the AI balance stayed untouched — confirmed via `grep` that `smallTalk`/`humanizeReply`/`complete` all call the provider directly and were entirely ungated. Moving the gate+debit into `callLLM` (rather than patching each caller) closes this structurally, the same "single source of truth" reasoning `understand()`'s own wrapper used originally. Re-verified live: a real reply now debits both balances correctly, and draining the AI balance to 0 degrades gracefully to the local/deterministic reply with zero balance/payment disclosure and no message-balance side effect.
- **Real regression found and fixed the same day**: every subscription that existed before this shipped has `messageBalanceKes`/`aiBalanceKes` at their schema default of 0 — the full local regression suite went from 73/73 to 31/73 passing the moment the gate went live, every failure the balance-exhausted fallback. Fixed with a one-time, per-subscription, idempotent migration (`balanceMigratedAt`, `scripts/prod-start.mjs`, runs every boot like the existing WhatsApp-number-routing reconciliation) that grants a configurable starting balance (`migration_grant_messages_kes`/`migration_grant_ai_kes`, defaults 500/250 KES) to any real non-trial, non-Enterprise subscription that predates the gate — never re-granted to a subscription that later legitimately runs its balance to 0 through real usage.
- **Low-balance notifications shipped, 2026-08-25**: `checkAndNotifyLowBalance()` (`prepaid-billing.ts`), fired fire-and-forget from both `debitMessageBalance`/`debitAiBalance` so it never slows a real reply. One combined notification (never two) when both balances are low at once, via both SMS (`Subscription.billingPhone`, honest skip if unset or SMS unconfigured) and email (`resolveTenantRecipientEmail()`, the same owner-resolution helper the cancellation invoice already uses). Per-balance `messageLowBalanceNotifiedAt`/`aiLowBalanceNotifiedAt` fire once per crossing and clear on the next check after a top-up brings a balance back above threshold — live-verified: a crossing notified once, a second message at the same low balance did NOT re-notify, and a top-up + one more message cleared both flags cleanly. Dashboard bell (`dashboard/layout.tsx`, reusing the existing live-computed `NotifItem` array — no new persistence) shows the same combined, per-balance-named warning, linking to `/dashboard/billing`. **Found in verification, not a bug in this feature**: the email send itself fails in the current environment — `RESEND_API_KEY` is a Resend sandbox key restricted to the account owner's own verified address, a pre-existing limitation shared by every email this codebase sends (including the cancellation invoice), not something new. Logged honestly (`console.error`) rather than silently swallowed, so it's visible whenever it's addressed.
- **Still open, not yet built**: the top-up flow (M-Pesa, targeting a specific balance), the `/onboard` flow changes (remove card-on-file, trial-first with no plan selection, one-trial-per-phone via the existing `OtpChallenge` table, admin override for legitimate re-signups), and admin UI for the new configurable settings.

### 6. RESOLVED, 2026-08-25 — self-service upgrade activated with ZERO payment; replaced with a real invoice-centric paid-upgrade flow
- **Category**: money-billing, critical
- **Found by**: direct user report — real, live production behavior: clicking "Upgrade" on `/dashboard/billing` immediately moved a tenant to a higher-priced plan with no payment collected of any kind.
- **Confirmed by re-reading the actual code** (`upgradeSubscriptionPlanAction`, `src/lib/actions.ts`, now deleted): a bare `db.subscription.update({ data: { planId } })`. No `computeBill()` call, no `Payment` row created, no `stkPush()`, no Stripe charge, no confirmation gate. An emergency stopgap disabled self-service upgrade entirely the same day while the real fix was designed (a full plan, reviewed and amended by the user before any code was written — see the session's plan file for the full spec).
- **Real fix shipped same day — invoice-centric architecture** (`src/lib/invoicing.ts`, `invoice-settlement.ts`, `proration.ts`, new `Invoice` Prisma model): the Invoice is the primary billing reference, not a phone number or account id. `createUpgradeInvoiceAction` computes proration server-side (never trusts a client-submitted amount — there is no client-submitted amount field anywhere in this flow) using real EAT (UTC+3, no DST) calendar-day indices, not raw millisecond division — verified immune to midnight-boundary artifacts. `settleInvoice` is the ONE function that ever moves an invoice `awaiting_payment → paid` and applies the plan change, inside a single `db.$transaction()` with a compare-and-swap `updateMany` guard on invoice status — atomic, so a crash between the invoice and subscription writes is structurally impossible, and a duplicate webhook/concurrent zero-payable settlement can only ever win once. `Payment.invoicePendingKey` (real `@unique` DB constraint, not an app-level check-then-act) prevents double-click/multi-tab/retry from firing two STK pushes for the same invoice — the same fix was also applied to the pre-existing regular-bill payment flow (`startPaymentAction`), which had the identical gap plus a separate one: it trusted a client-submitted `amount` field with no server-side cross-check at all, now computed server-side via `computeBill()`.
- **Real gap caught in testing before shipping**: without an explicit guard, "upgrading" to Enterprise (`priceMonthly: 0`, negotiated-contract plan) would always compute `payableKes = 0` and auto-settle for free through the same real zero-invoice path a legitimate full-credit upgrade uses. Fixed by excluding any `Plan.postpaidUsage` plan from self-service entirely, both in the UI list and server-side.
- **STK self-service upgrade flow deployed and backend-verified** — real Safaricom Daraja sandbox STK push, real callback, exact settlement — not just typechecked: real tenant login (Kilimani Retail), 15-days-into-a-30-day-cycle upgrade Starter→Professional — invoice showed exact proration (`remaining KES 750`, `payable KES 4,150`), the STK push fired, simulated callback settled the invoice, subscription plan changed, `messageBalanceKes`/`aiBalanceKes`/connectors all confirmed untouched, full `invoice.created → invoice.settled` audit trail. Replayed the identical callback — confirmed exactly one settlement, no double-apply. Constructed and verified the zero-payable edge case (temporarily inflated a plan price) — real `KES 0` invoice went through the identical `settleInvoice()` path, not a bypass. Pure proration math additionally verified against real Feb 28/29-day months, 30/31-day months, past-renewal clamping, and the trial-tenant zero-credit case. **Production deployment is healthy** — schema migrated cleanly, routes live, UI renders correctly — **but a real production live-money acceptance test was intentionally NOT performed**, to avoid firing an uncontrolled real Daraja transaction. Record this precisely: "deployed and backend-verified" is not the same claim as "a real production payment was completed" — it wasn't, on purpose.
- Paybill shipped 2026-08-25 too — see item 7 below.

### 7. RESOLVED, 2026-08-25 — Paybill support added to the same invoice engine (not a second payment system)
- **Category**: money-billing
- **Why this needed real care, not a quick add**: unlike STK (an amount P2Less controls, initiated by P2Less), Paybill is customer-initiated — the payer types their own amount and reference into their own M-Pesa app. That reintroduces every risk STK structurally couldn't produce: partial payment, overpayment, a mistyped reference, money arriving against an invoice that's already paid/cancelled/expired.
- **First draft rejected in review**: the invoice lookup was `findFirst({ status: "awaiting_payment" })` then compare-in-JS — with more than one awaiting invoice in the table, this could silently match the wrong one. Fixed with `Invoice.normalizedInvoiceNumber` (uppercased, non-alphanumeric stripped), a real unique-indexed column, looked up directly — a genuine DB-backed exact match, never a scan. Tolerates formatting ("INV-2026-000123" / "inv 2026 000123" / "INV2026000123" all resolve identically) while a genuinely different invoice number resolves to nothing.
- **`settleInvoice()` restructured to resolve invoice STATE before deciding what a payment means** — paid/cancelled are real terminal states (further money is evidence of a duplicate, never a second upgrade); an `awaiting_payment` invoice past `invoice_expiry_hours` now gets its `"expired"` status genuinely **written**, not just computed on the fly at read time as before; only a real `awaiting_payment`, non-expired invoice proceeds to sum every `"paid"` `Payment` against it and settle once that sum reaches `payableKes` — real, tested support for partial and multi-payment settlement, individual `Payment` rows never mutated or combined, the invoice is the aggregate. Excess on overpayment is confirmed never applied anywhere else (no balance, no credit) — forfeited, per the already-decided rule.
- **Real production-adjacent bug found and fixed during implementation**: `settleInvoice()` called `getSettingNumber()` and `audit()` — both of which use the plain, non-transactional `db` client — from *inside* an open `db.$transaction()`. On SQLite (single-writer) this self-blocks the connection against its own open transaction, consistently timing out at Prisma's 5000ms default. Fixed by resolving `invoice_expiry_hours` before ever opening a transaction, and by making `audit()` the responsibility of whichever caller owns the *outermost* transaction, called only after it has actually committed. Caught live via real repeated timeouts during testing, not by code review alone — confirmed fixed by checking that a real settlement now produces exactly one audit entry, not several orphaned ones.
- **Live-verified**, full scenario matrix, real seeded tenant: exact-amount payment settles; underpayment stays `awaiting_payment` with the real partial amount recorded as evidence (never shown as "upgraded"); a second payment reaching the cumulative total settles then, exactly once; **two payments fired truly concurrently, each individually insufficient, summing to exactly the threshold — settled exactly once, one audit entry, one upgrade** (the specific race the review flagged as where real financial bugs hide); overpayment settles immediately with the real amount retained as evidence and the excess confirmed not applied anywhere; payment against an already-paid invoice recorded as evidence only, no second upgrade; payment against a 48-hours-old (expired) invoice correctly persists the real `"expired"` transition, no upgrade; payment against a cancelled invoice recorded as evidence only; two invoices with the identical payable amount — a payment referencing one never touched the other, confirming amount is never the match key; a payment from a phone number different from any on file still settled correctly, confirming payer phone is evidence, never identity; a genuinely wrong invoice reference fell through cleanly to the existing `UnmatchedTransaction` safety net, never guessed; duplicate `TransID` delivery produced no second `Payment` and no second audit entry; the existing STK flow re-verified end to end afterward to confirm the shared `settleInvoice()` refactor changed nothing about its behavior.
- **Still open, tracked as separate later stages, not silently dropped**: Visa/Card via Stripe (today only `$0` SetupIntent card-verification exists — zero PaymentIntent/Checkout/webhook code anywhere, a genuinely new subsystem) shows as visibly disabled "Coming soon." Admin reconciliation UI is not yet invoice-aware (a genuinely unmatchable Paybill payment still lands in the existing tenant-only `UnmatchedTransaction` flow). The broader app-wide sweep replacing `window.confirm()`/toast-only destructive-action confirmations with `src/components/modal.tsx` is also separate future work.

### 8. RESOLVED, 2026-08-25 — Visa/Card via Stripe added, the third and last payment method on the same invoice engine
- **Category**: money-billing
- **What shipped**: real card charging via Stripe's hosted Checkout (not a custom card form — zero PCI scope in this app, Stripe's own hosted page handles card entry). `createUpgradeInvoiceAction`'s invoice, `settleInvoice()`'s settlement, `Payment.invoicePendingKey`'s double-click protection — all reused exactly as STK/Paybill already established, no new settlement logic written. This is genuinely new infrastructure in one respect: the **first Stripe webhook route in this codebase**, and only the fourth webhook overall to verify a cryptographic signature (after WhatsApp, Messenger, and Resend/email) — a bad `Stripe-Signature` is rejected with a real `400`, never swallowed as `200` the way a malformed M-Pesa payload is, since a forged webhook here is a real attack surface, not a delivery quirk.
- **One fact verified live before writing dependent code, not assumed from documentation alone**: whether KES is a zero-decimal or two-decimal currency in Stripe (this is a real, not academic, 100x-over/undercharge risk — several other African currencies genuinely are zero-decimal in Stripe's API). Confirmed by creating a real test-mode Checkout Session for a known amount and reading the actual rendered price on Stripe's real hosted page: `payableKes: 4150` → `unit_amount: 415000` → the page genuinely displayed **"KES 4,150.00"**, confirming KES is two-decimal (cents) and the `× 100` conversion is correct.
- **Live-verified end to end for real, not via crafted payloads alone**: unlike STK (Daraja sandbox, reachable) and Paybill (never had a real registered endpoint), Stripe's Checkout Session creation and redirect genuinely could be tested for real — real tenant login, real click through to Stripe's actual hosted test-mode Checkout page, a real completed payment using Stripe's own test card (`4242 4242 4242 4242`, moves zero real money by design), a real redirect back to `/dashboard/billing?upgrade=success`. Confirmed the page shows an honest **"Payment received — confirming now"** message at that point, never a premature "upgraded" claim — the plan still correctly showed Starter, since real webhook delivery can't reach a local dev box without a public tunnel. Settlement itself was then completed and verified via a self-signed `checkout.session.completed` payload (same HMAC-over-`{timestamp}.{body}` scheme Stripe's SDK itself verifies, signed with the local dev webhook secret) — confirmed the invoice settled, the subscription upgraded to Professional, and exactly one `invoice.settled` audit entry was written.
- **Also verified**: invalid/tampered signature rejected with a real `400`, nothing recorded or processed; a genuine duplicate `event.id` delivered twice produced no second settlement; a payment-shaped event delivered against an *already-settled* invoice was correctly recorded as evidence only (`invoice.payment_after_settlement`, no second upgrade) and the true replay of that same event was separately deduplicated — both real, distinct scenarios confirmed independently; `checkout.session.expired` correctly marked the pending `Payment` `failed` and cleared `invoicePendingKey` so a retry can create a fresh session.
- **Production webhook registered and live-verified, 2026-08-25**: a real webhook endpoint (`we_1U8FhoLU2xVI8aJzyinT8Fos`) was created via the Stripe API against `https://p2less-app-production.up.railway.app/api/payments/stripe/webhook`, subscribed to `checkout.session.completed` + `checkout.session.expired`, and the real returned signing secret was set as `STRIPE_WEBHOOK_SECRET` in Railway's production environment (redeployed to pick it up). This closes the one piece Stage C's original verification couldn't reach — a genuinely Stripe-delivered, Stripe-signed webhook hitting the real production route, as opposed to only a self-signed payload. Verified for real: created a real Checkout Session via the API and immediately expired it (a real Stripe action, not a crafted payload), which caused Stripe's own infrastructure to deliver a real signed `checkout.session.expired` event (`evt_1U8FnTLU2xVI8aJzZpG2JoN1`) to the production endpoint — confirmed via a temporary debug route (removed in the very next commit, same pattern as the schema-verification routes earlier this session) reading the `InboundEvent` row directly: `processingStatus: "processed"`, `responseStatus: 200`, `error: null`. Since an invalid signature is rejected before an `InboundEvent` row is ever written, this row's existence is itself proof the real signature verification path works end to end in production.
- **Still deliberately gated in production**: `PaymentChannel.implemented` for `"card"` stays `false`. Registering the webhook was necessary but not sufficient to go live — production's `STRIPE_SECRET_KEY` is still the same **test-mode** key used in local dev (confirmed via `railway variables`), so a real customer's real card would simply fail against Stripe's test-mode API, not charge. Flipping the channel on today would show real customers a Card option that cannot actually take their money. Turning Card on for real requires a live-mode Stripe key pair in Railway's environment, in addition to a live-mode webhook registered against that live key (test-mode and live-mode webhooks are separate registrations in Stripe) — both genuinely new external-account steps, not something already done. `scripts/sync-integrations-catalog.ts` (standalone, not invoked by `prod-start.mjs` on boot) is still the mechanism to flip the flag once that's ready.
- **Still open, tracked as separate later stages, not silently dropped**: refunds/reversals, invoice-aware admin reconciliation, the broader `window.confirm()` → real-modal sweep, and the live-mode Stripe key migration described above.

### 9. RESOLVED, 2026-08-25 — Invoice-aware manual reconciliation added
- **Category**: money-billing
- **The gap**: STK/Paybill/Card all converge on `settleInvoice()`, but when a payment's automatic invoice matching fails (a customer typos the invoice number into a Paybill reference; an STK callback reports an amount that doesn't match what was invoiced), the only manual-resolution paths that existed (`matchUnmatchedTransactionAction`, `resolvePaymentUnknownAction`) could only attach evidence to a **tenant's recurring monthly bill** — there was no way for an admin to attach it to the specific awaiting **invoice** it actually belonged to.
- **What shipped**: `matchUnmatchedTransactionToInvoiceAction` (new) and `resolvePaymentUnknownAction` (fixed) — both now settle the correct invoice via the same `settleInvoice()` authority every automatic channel uses, no new settlement logic written. New admin UI: a "Match to invoice" action alongside the existing tenant-match button, with a live invoice search (exact `normalizedInvoiceNumber` match, never fuzzy) and an "Expected result" preview panel (payable, already paid, this payment, resulting total, would-settle-or-not) shown before the admin confirms — explicitly labeled advisory, since the write path always reloads and recomputes for real regardless of what the preview showed.
- **Security boundary, explicitly tested, not just implemented**: invoice search is scoped to the admin's own `adminScope` (a tenant-restricted admin never sees another tenant's invoices in search results), and — the actual security boundary, not the UI convenience — the write action independently re-checks the loaded invoice's real tenant against the admin's scope, rejecting a bare out-of-scope `invoiceId` submitted directly, bypassing the UI entirely. Verified live: a real scoped admin (`finance_admin` role, `adminScope` restricted to one tenant) attempting to match against another tenant's real invoice was rejected with `"Invoice outside your assigned scope."` before any transaction opened — no `Payment` created, no `matchedInvoiceId` set, no settlement, no subscription change.
- **A real, pre-existing bug found and fixed during this stage's live verification, not introduced by it**: `resolvePaymentUnknownAction`'s initial `db.payment.findUnique()` ran before any tenant context was established, so the 2026-08-23/24 tenant-isolation fail-closed hardening rejected it outright with `TenantContextMissingError` — this broke the **original** tenant-only "unknown payment" resolution too, not just the new invoice-aware branch, meaning the "Resolve: paid"/"Resolve: failed" buttons on `/admin/reconciliation` were silently non-functional before this fix. Fixed with `runCrossTenant()`, the same pattern every webhook route already uses for this exact situation. Confirmed live: an STK-initiated, invoice-linked payment reproducing the real amount-mismatch path (`mpesa/callback/route.ts`) landed in `"unknown"`, and resolving it "paid" from the admin UI now correctly calls `settleInvoice()` and upgrades the subscription — proven via the resulting `invoice.settled` audit entry and the subscription's `planId` matching the invoice's `toPlanId`.

The pattern behind today's incident — a missing database-level constraint letting bad state exist that application code alone should have prevented — is worth watching for specifically when reviewing any future *new* channel/connector/external-identity feature: does the schema itself enforce the invariant, or only a code path that could be bypassed by a second code path nobody thought to check.
